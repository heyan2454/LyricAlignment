# gate 的分数阶梯：每加一个免费信号能多兑现多少天花板（第 36–38 轮，2026-09-12）

> 数字由 `runs/20260912_gate_band_policy/GATE_BAND_POLICY.json` 生成。阈值**只在拟合片上选**、在**不相交评估片**上测；天花板在**同一评估片**重算 ⇒ 两者可直接相减。零新前向、零 GPU。
> R5 不是可用模型，只是「如果探测器完美」的参照，用来验证框架自洽。

## 0. 结论

- **200ms 边、5% 误放预算**：只用熵放行 76.30% / 72.70%（两折叠），等权加上倒序+间隙残余后 **85.01% / 80.59%**（+8.7pp / +7.9pp）；距天花板 87.3% 的余量从 ~11.0pp 缩到 ~2.3pp。
- **只加倒序基本不涨**（R2 = 76.19% / 75.81%）⇒ 与第 32 轮一致：倒序预示的是后续塌陷，不是端点精度，作为端点 gate 的成分它没有增量。
- **第 27 轮的融合分位（R4 = 75.88% / 75.08%）没兑现 R3 的收益**：它让 0/1 常量般的倒序与大面积缺失的间隙一起参与平均，权重被 NaN 稀释 ⇒ **对含缺失值的免费信号，等权分位平均比「含缺失即跳过」的融合更实用**（这是对第 27 轮做法的修正）。
- **R5 oracle 贴着天花板**（GTSinger headroom 在 −3.5~+0.2pp、M4 +0.12~+0.36pp、误放 0%）⇒ 框架自洽。oracle 在 GTSinger 上略超天花板属正常：阈值定在拟合片，评估片实现会带小误放，而天花板定义的是「零风险放行」的上限。
- **关键限定**：R3 的收益来自 `gap_over_core`，而它**跨语料复现未通过**（第 30/31 轮：M4 ρ=−0.06、AUC 0.506，且 M4 面板被判定不可比）。因此 R3 只是 **GTSinger 口径内的上限证据，不得上线**；要用它，必须先在有真值的伴奏数据上重新证明（即那份 3–5 首人工标注实验）。

## 2. M4Singer 长时序：真实分数全档不可行，oracle 贴着低天花板

- **train->validation**（fit 91,845 / eval 21,773，评估片真 unsafe **69.8%**）：R1–R4 在三个边、两种预算下**全部不可行**；R5 oracle 可达 ≤100ms 4.32%、≤160ms 15.68%、≤200ms 22.83%（天花板 4.68%、15.92%、22.95%，误放 0%）
- **train->test (transfer only)**（fit 91,845 / eval 20,920，评估片真 unsafe **82.3%**）：R1–R4 在三个边、两种预算下**全部不可行**；R5 oracle 可达 ≤100ms 2.84%、≤160ms 8.49%、≤200ms 12.26%（天花板 3.10%、8.49%、12.27%，误放 0%）

⇒ 在普遍错的数据上，「低误放预算」与「高放行率」在数学上不可能同时成立；此时 gate 的正确行为就是几乎不放行并报警，而不是硬找阈值。

## 3. 反向需求：要把 gate 做到 X% 自动放行，需要什么强度的分数

- GTSinger · 200ms 边 · 5% 预算这条路径上：熵 76.3% → 熵+倒序 76.2% → +间隙残余 85.0% → oracle 90.8% → 零风险天花板 87.3%。**再往上没有空间**：超出天花板只能以增加误放为代价；
- 160ms 边的天花板 86.2% 与 200ms 边的 87.3% 相近，但 R1 在 160ms 的余量是 20.2pp（vs 200ms 的 11.0pp）⇒ **放宽带边不仅格点稳定，也把「可达成的放行率」抬高**；
- M4 上零风险天花板本身只有 ~23%，所以那里的问题不是「分数不够好」，而是**这条链路的产物质量不支持自动化**（与第 8/30 轮一致）。
